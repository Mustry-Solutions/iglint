# iglint design

iglint is a fast linter for Inductive Automation Ignition 8.3 projects, written
in Rust. It lints Perspective views, every kind of Jython 2.7 script, Ignition
expressions, project-wide references, style classes and gateway resources.

This document is the contract between the crates. Read it before changing a
crate boundary.

## Principles

1. **Correct before fast, fast by design.** Every finding must be right. A false
   positive is a bug. Speed comes from architecture (one parse per file, no
   subprocesses, data parallelism), never from skipping work.
2. **Exact Jython.** Ignition runs scripts on Jython 2.7 (IA fork 2.7.3). Our
   parser accepts exactly what that parser accepts and produces the same AST.
   It is tested differentially against the real Jython parser (see
   `oracle/`).
3. **Byte-exact files.** Fixes are text edits on the original bytes. A fix never
   reformats anything it does not change.
4. **Precise locations.** Every diagnostic points to a byte range in the real
   file on disk, including diagnostics inside scripts and expressions that are
   embedded as JSON strings.
5. **No customer data in this repository.** See "Private corpora" below.

## Crates

| Crate | Responsibility |
|---|---|
| `iglint_text` | `TextSize`, `TextRange`, `LineIndex`, `TextEdit`, `apply_edits`. |
| `iglint_json` | Lossless, span-preserving JSON parser. Every value and key keeps its byte range; strings keep raw and decoded forms plus an offset map from decoded to raw offsets so embedded code can be mapped back to the file. Helpers to build minimal edits (remove a member, rename a key, replace a value) that preserve formatting. |
| `iglint_python` | Jython 2.7 lexer, parser and AST (node set identical to Python 2.7 `_ast`), visitor, `ast.dump`-compatible printer, error recovery. No Ignition knowledge. |
| `iglint_python_semantic` | Scopes, bindings and references with Python 2.7 semantics as Jython compiles them (list comprehensions leak, `exec` and `import *` make scopes dynamic, no `nonlocal`, class bodies read by name, private names mangled, the reads the interpreter makes by itself). Builtins of Jython 2.7. Takes injected names from the caller. |
| `iglint_expression` | Ignition expression language: lexer, parser, AST, references (`{...}` property and tag references), function calls. |
| `iglint_stubs` | Generated facts about Ignition 8.3: `system.*` scripting API, expression functions, Perspective component types and their properties. Data is generated by introspecting a real gateway (`stubs-gen/`). |
| `iglint_project` | Discovery of 8.3 projects and gateway resources, resource model, Perspective view model (components, properties, bindings, transforms, scripts, events, message handlers, custom methods), project index used for cross-resource checks. |
| `iglint_linter` | Diagnostics, rule registry and metadata, the rules themselves, suppressions, baseline, fix application, the check driver (parallel over files), cache. |
| `iglint_config` | `iglint.toml` / `[tool.iglint]` loading, resolution of per-path settings, reading legacy ign-lint `rule_config.json` and whitelist files, `migrate`. |
| `iglint_server` | Language server (LSP) on top of the linter. |
| `iglint` | The binary: CLI, output formats, ign-lint compatible mode. |

Dependency direction: `text <- json, python, expression <- python_semantic <-
project <- linter <- config? <- server, iglint`. `iglint_config` depends only
on `iglint_linter` metadata types (rule codes and option schemas). No crate
below `iglint_linter` knows about rules or severities.

## Scripts embedded in views

Perspective stores only a function body. Ignition compiles it inside a
generated `def` header. We do the same:

| Location | Header |
|---|---|
| component and view event script action | `def runAction(self, event):` |
| script transform | `def transform(self, value, quality, timestamp):` |
| property change script (`propConfig.*.onChange`) | `def valueChanged(self, previousValue, currentValue, origin, missedEvents):` |
| message handler | `def onMessageReceived(self, payload):` |
| custom method | `def <name>(self, <params...>):` |

(The exact list, including session events, page events and gateway/webdev
scripts, lives in `iglint_project` and is verified against the real gateway.)

The wrapped source is parsed as a module. A `SourceMap` maps every offset in
the wrapped source back to a byte offset in the JSON file, through the JSON
string's escape map. Diagnostics in generated header text are clamped to the
script property's key.

## Diagnostics

```text
Diagnostic {
  rule: RuleCode,              // "VIEW001"
  severity: Severity,          // Error | Warning | Info
  message: String,
  file: FileId,
  range: TextRange,            // in the file on disk
  node_path: Option<String>,   // e.g. "root/Container/Button.props.text" (iglint_project::node_path); ign-lint paths are also modelled for parity output
  labels: Vec<Label>,          // secondary ranges
  fix: Option<Fix>,            // Fix { applicability: Safe | Unsafe, message, edits: Vec<(FileId, TextEdit)> }
  fingerprint: u64,            // stable across line moves; used by the baseline
}
```

## Rules

Every rule has a stable code (`VIEW001`), a kebab-case name
(`unused-custom-property`), a category, a default severity, whether it is in
the default set, whether it can fix, an options schema and Markdown docs with
"bad" and "good" examples. Config and suppressions accept the code or the name.

Categories: `VIEW` (view structure), `NAME` (naming), `BIND` (bindings and
expressions), `SCR` (script correctness), `REF` (cross-resource references),
`PERF`, `SEC`, `A11Y`, `STYLE`, `TAG`. Rules that correspond to an ign-lint
check live in the category of what they check (`iglint migrate` and a
legacy `rule_config.json` map ign-lint's rules to them); there is no
separate compatibility category.

Rules are visitors over typed contexts (view, component, property, binding,
expression, script, project index, resource). The driver collects all
enabled rules once and walks each file once.

## Suppressions and baseline

* Scripts: `# iglint: ignore[SCR001]` on the line, `# iglint: ignore-file[...]`.
* Views: no markers inside `view.json`; use config `exclude`, per-rule
  `exclude`, `[[overrides]]`, or the baseline.
* Baseline: `.iglint-baseline.json` with fingerprints. Only new findings fail.
* ign-lint whitelist files are honoured (whole-file skip) for compatibility.

## Performance

Target: at least 10x faster than ign-lint with its best configuration, on every
corpus. Files are processed in parallel with `rayon`. Each file is read once,
parsed once. Project-wide checks use an index built from per-file summaries.
A content-hash cache makes unchanged files free on the next run.

## Private corpora

The Ignition project used for benchmarking during development belongs to a
customer. Rules:

* Its path is only ever passed through the `IGLINT_PRIVATE_CORPUS` environment
  variable. Never hard-code it.
* Nothing derived from it is committed: no snippets, file names, view names,
  identifiers, snapshots, or counts beyond aggregate numbers (file count, total
  size, timings).
* Tests that need it are `#[ignore]` and print only aggregate results.
* `scripts/check-no-leak.sh` scans the repository for forbidden markers and runs
  in CI.

Public test material is hand-written, generated by `bench/gen`, or taken from
the Python 2.7 standard library shipped with Jython.

## Oracle

`oracle/` runs IA's Jython (from the `inductiveautomation/ignition:8.3.3`
Docker image) to produce `ast.dump(..., include_attributes=True)` output and
syntax errors for a set of files. Parser tests compare our dump with Jython's. The same image's compiler is the
reference for name resolution: `oracle/scope/` records which frame
accessor Jython's code generator picks for every name (and how it mangles
private names), and the semantic model must produce the same.
